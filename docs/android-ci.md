# Android 发布流水线

## 分工

- `verify`：锁定依赖、静态检查、Flutter 测试、发布保护测试。没有生产 Environment 或生产密钥。
- `build`：与 verify 并行，使用原签名与完整设备架构构建、验签，随后保存同一次运行的 APK、清单、SHA-256、来源提交和 Run ID。产物保留 30 天，测试失败也能下载已成功构建的产物，但不会发布。
- `publish`：只有前两项成功才运行；下载当前 Run ID 的产物，不重新编译。上传失败后在该次运行重跑失败 Job 即可。过期/被清理的产物须重新构建，不能拿另一次运行的产物冒充。

校验/编译可以被新提交取消，发布全局串行且不主动中断。GitHub 排队不保证先后顺序，因此发布前和更新清单前都检查版本号。手动旧版本会跳过；相同版本号但不同 APK 拒绝覆盖。

## 上传与缓存

- Flutter/Pub 原缓存保留。Gradle 只缓存下载的依赖和 Wrapper；当前分支可读写，不缓存证书、local.properties、整个项目或配置缓存。
- 8 MiB 分片、10 路并发，标准有限重试；每 15 秒显示传输进度与平均速度。
- 上传后的对象大小及 SHA-256 元数据必须匹配；最后才用条件写入更新 `latest.json`。对 ETag 冲突或不支持条件写入的存储服务不作无条件覆盖降级，保留原入口和构建产物。
- 在首次正常发布中确认雨云支持条件清单写入。如果失败，先检查错误阶段与存储兼容性，不通过删除校验或强制覆盖来绕过。
- 保留原版本计算、APK 对象路径、production flavor、签名、下载入口和清单字段。未配置新服务器或付费构建服务。

## 验证与观察

`python -m unittest discover -s tools/tests -p test_publish_android_release.py -v`

测试使用内存对象存储，不连接雨云。覆盖上传失败、远端校验失败、重跑复用、旧版本、同版本冲突、新旧任务交错、最后一次检查后的竞争、产物篡改、跨运行产物、失败退出码及发布依赖门禁。

本轮本地验证：工具测试共 32 项通过（其中新增发布保护测试 12 项），工作流 YAML 解析及 15 段 Bash 命令语法检查通过。尚未提交推送或执行改造后的 GitHub Actions，也未向雨云试写；真实上传速度和条件写入兼容性留待下一次正常发布确认。
